# 第28章 晶圓廠數據體系——AI應用的數據地基

> 本章是全書的數據基礎設施章節。前面幾章介紹了晶圓廠的三大核心部門與業務場景,從本章開始,我們將進入「AI如何落地」的實質討論。而AI落地的第一步,是搞清楚一個問題:**晶圓廠的數據到底長什麼樣?**

在前面幾章的討論中,我們已經反覆提到FDC訊號、量測數據、MES記錄、良率數據等概念。本章將系統地回答三個問題:晶圓廠有哪些數據、為什麼這些數據如此難管理、如何把這些數據整理成AI可以可靠消費的形態。理解本章內容,是理解後續良率預測、虛擬量測、設備預測性維護、根因分析等所有AI應用的前提——因為**模型的精度上限,由數據的品質與語義清晰度決定**。

本章內容分為六節:28.1晶圓廠數據全景,建立對七大核心數據源的整體認知;28.2數據血緣與隱性知識,剖析數據「從哪來、到哪去、誰懂它」;28.3數據治理體系,討論讓數據可信、可追溯、可複用的方法;28.4工業語義層與知識圖譜,介紹讓AI「讀懂」晶圓廠語言的關鍵技術;28.5 LLM與Agent的數據消費模式,探討大模型如何安全地使用這些數據;28.6落地路徑與分階段實施,給出從數據到價值的務實路線圖。

## 28.1 晶圓廠數據全景:從MES到設備日誌

> **本節核心問題**:晶圓廠到底有哪些核心數據源?它們各自的特徵是什麼?為什麼必須把它們關聯起來使用?

如果請一位IT工程師畫出晶圓廠的系統地圖,他會畫出一張由MES、EAP、FDC、SPC、YMS、ERP等系統組成的複雜網路;如果請一位製程工程師描述一天的工作,他講的是「這批Wafer在某台Etcher上跑了一個Recipe,良率有點問題」。這兩張圖之間的差距,就是本章要彌合的。本節從數據角度,把晶圓廠「解剖」一遍。

### 28.1.1 核心數據源地圖

晶圓廠的數據源可以概括為七大核心系統。它們分佈在IT/OT分層架構的不同層級,各自扮演不同的角色:

**MES(Manufacturing Execution System,製造執行系統)** 是晶圓廠的「生產總調度」。它記錄每一批Lot的製程路線(Route)、每一步驟(Step)的執行狀態、在製品(WIP)分佈、工單資訊、操作員與設備的互動記錄。MES回答的問題是「哪批晶圓現在在哪裡、做了什麼、接下來做什麼」。它是批次級、事件級數據的核心來源,也是其他系統數據的「錨點」。

**FDC/EDA(Fault Detection and Classification,故障檢測與分類 / Equipment Data Acquisition,設備數據採集)** 是設備製程參數的「記錄儀」。EDA負責從設備採集高頻時序數據(溫度、壓力、RF功率、氣體流量等),FDC在採集基礎上進行統計監控與異常檢測——當某個參數偏離製程窗口時觸發警報。FDC數據回答的問題是「這批Wafer在加工的那幾分鐘裡,設備狀態是否正常」。這是全廠**頻率最高、單量最大**的數據流。

**SPC(Statistical Process Control,統計製程管制)** 系統基於量測數據(膜厚、CD、套刻精度等)繪製管制圖,監控製程是否處於受控狀態。SPC與FDC的區別在於:SPC監控的是**製程結果**(量測得到的參數),FDC監控的是**製程條件**(設備運行參數)。兩者互為補充。

**YMS(Yield Management System,良率管理系統)** 彙集電性測試(CP/FT)與缺陷檢測數據,生成晶圓圖(Wafer Map)、良率趨勢與缺陷分佈分析。YMS回答的問題是「這批晶圓最終做得好不好、壞在哪裡」。

**ERP(Enterprise Resource Planning,企業資源規劃)** 管理物料、採購、庫存、成本、訂單等企業資源層面的數據。它不直接參與製程,但對產能規劃、成本分析、供應鏈決策至關重要。

**SECS/GEM設備日誌(SEMI Equipment Communications Standard,設備通信標準 / Generic Equipment Model,通用設備模型)** 是設備與主機系統通信的工業協定層。透過SECS/GEM,設備上報製程配方(Recipe)執行記錄、警報事件、狀態變遷(如Process End、Alarm)。這些日誌是理解「設備實際做了什麼」的第一手資料,也是FDC數據的原始載體。

**檢測/量測系統(KLA缺陷掃描、CD-SEM、光學量測等)** 產生缺陷座標、缺陷影像、關鍵尺寸等數據。它們與YMS聯動,為缺陷分析和良率歸因提供最直接證據。

**數據源全景圖(架構圖說明)**:自下而上可分為四層。**設備層**(最底層)包括蝕刻機、微影機、薄膜設備等,透過SECS/GEM協定與上層通信,產生設備日誌與製程數據;**控制層**包括EAP(Equipment Automation Program,設備自動化程式)、FDC/EDA,負責設備自動控制與製程數據採集;**執行層**包括MES、SPC、YMS,承載生產執行與品質監控的核心業務;**計畫層**(最頂層)包括ERP與各類分析平台,面向企業資源與經營決策。數據流向自下而上:設備層產生原始製程數據,控制層做採集與初篩,執行層組織成業務記錄,計畫層進行全域分析。

以某批晶圓為線索可以把這條鏈路串起來:一片Wafer投入產線後,**MES**為其分配Lot編號並規劃製程路線;在某個蝕刻步驟,設備透過**SECS/GEM**上報加工開始與結束事件,**FDC/EDA**以毫秒級頻率記錄腔體溫度、壓力、RF功率等製程參數;加工完成後,量測設備產生**CD-SEM/光學量測**數據,**SPC**判斷該步驟是否受控;最終,這批晶圓經過電性測試,**YMS**生成晶圓圖與良率統計。一條完整的數據鏈就這樣形成了。

### 28.1.2 數據特徵對比:時序粒度、量級與更新頻率

不同類型的數據,其時間粒度、數據量級與更新頻率差異巨大。理解這些差異,是選擇儲存方案與AI建模方式的前提。

我們以**某道蝕刻製程的FDC trace數據**為例來說明時序特徵。蝕刻機腔體在加工一片Wafer時,FDC系統通常會以1-10Hz的頻率採集數十個通道的參數(腔體壓力、上下電極RF功率、溫度、各氣體流量、ESC靜電吸盤電流等)。以20個通道、5Hz採樣、單次加工200秒計算,一片Wafer就產生約2萬條記錄;一個腔體一天加工數百片,單台設備單日就產生數百萬條FDC記錄。這是典型的**高頻時序流**。

與之形成鮮明對比:**MES批次事件**是分鐘到小時級的——一個Lot完成一步製程才產生一條記錄;YMS良率數據是批次級或日級——通常按Lot彙總或按日彙總。

以下表格對比了七大核心數據源的特徵:

| 數據源 | 典型欄位 | 時間粒度 | 單日數據量(參考) | 更新方式 |
| --- | --- | --- | --- | --- |
| MES | Lot ID、Route、Step、狀態、時間戳 | 分鐘~小時級 | 萬級~十萬級記錄 | 即時事件推送 |
| FDC/EDA | 通道ID、壓力、溫度、RF功率、時間戳 | 毫秒~秒級 | 百萬~千萬級記錄 | 即時串流寫入 |
| SPC | 參數ID、量測值、UCL/LCL、判定結果 | 批次級 | 千~萬級記錄 | 批次處理+即時預警 |
| YMS | Lot ID、良率值、缺陷座標、晶圓圖 | 批次級/日級 | 千級記錄+影像檔 | 批次處理 |
| ERP | 物料號、工單、成本、庫存 | 分鐘~天級 | 千級記錄 | 批次處理 |
| SECS/GEM日誌 | 事件ID、Recipe名、狀態碼、時間戳 | 秒~分鐘級 | 萬~十萬級事件 | 即時推送 |
| 檢測/量測系統 | 缺陷座標、缺陷類型、CD值、影像 | 片級/批次級 | 千級記錄+大量影像 | 批次處理+即時聯動 |

> **實踐提示:** 晶圓廠數據儲存的常見誤區是「一刀切」。FDC這類高頻時序數據適合用欄式儲存或時序資料庫(如InfluxDB、TimescaleDB)管理;MES/YMS這類業務數據適合用關聯式資料庫;檢測影像等非結構化數據需要物件儲存。先用數據特徵表做分類,再選儲存,能避免後期「查一次FDC歷史要跑幾分鐘」的尷尬。

從量級估算看,一座先進晶圓廠(月產數萬片12吋Wafer)的FDC歷史數據年增量可達TB級,加上檢測影像與量測數據,全廠數據年增量通常在數十TB量級。這個量級對儲存與查詢架構提出了明確要求:高頻製程數據必須考慮壓縮與分層儲存(熱數據線上、冷數據歸檔)。

### 28.1.3 數據之間的業務關聯

數據源地圖回答「有什麼數據」,數據關聯則回答「這些數據如何拼成完整故事」。晶圓廠AI應用的一個核心特徵是:**絕大多數有價值的分析任務都需要跨系統取數**。

以一次典型的良率下降根因分析為例:某批晶圓CP測試良率驟降,YED(良率工程)工程師需要同時查看:**YMS**的晶圓圖確定缺陷的空間分佈(是邊緣還是中心?)、**MES**的批次歷史確認這批Wafer經過了哪些設備、**FDC**數據查看對應設備在加工時的參數是否漂移、以及設備的**PM(Preventive Maintenance,預防性維護)記錄**確認是否臨近維護週期。任何一個單系統都無法回答「良率為什麼下降」——只有跨系統關聯,才能把「結果異常」追溯到「過程異常」再追溯到「設備異常」。

典型的數據關聯鏈可以表示為:

```
Lot ID → Equipment ID → Chamber ID → FDC Trace → 對應缺陷 → 良率損失
```

即:從良率損失出發,沿批次定位到加工設備與腔體,再下沉到該腔體的FDC過程數據,找出參數異常,與缺陷分佈比對,最終確認損失來源。這條鏈路正是第9章以後良率分析、根因分析類AI應用的數據基礎。

跨系統關聯在現實中並不容易,主要面臨三類難點:

**主鍵體系不一致。** 同一物理物件在不同系統中編碼可能不同。例如批次號在MES中是`LOT-2026-001`,在YMS中可能被截斷或加前綴;設備號在MES中是`ETCH-03`,在FDC系統中是`EQP-ETCH-003`。關聯的第一步往往是「對帳」,建立各系統主鍵的對映關係。

**時間對齊問題。** FDC數據的時間戳來自設備時鐘,MES事件時間戳來自伺服器時鐘,兩者可能存在秒級甚至分鐘級偏差。在做「加工時段內的FDC參數」這類關聯時,直接按時間戳join會得到錯誤結果,需要先做時鐘校準或使用事件邊界(如Process Start/End事件)對齊。

**多版本狀態。** 一批晶圓可能經歷返工(Rework)、Hold(凍結)、拆分合併,其製程歷史會形成多個版本。關聯時必須明確「取哪個版本」——通常取最終版本,但根因分析可能需要回看所有歷史版本。

> **本節小結:**
> - 晶圓廠數據源可概括為七大系統,MES、FDC/EDA、SPC、YMS、ERP、SECS/GEM日誌、檢測/量測系統各自扮演不同角色,分佈在IT/OT四層架構中。
> - 數據的時間粒度差異巨大:FDC是毫秒~秒級高頻流(單設備單日數百萬條),MES是分鐘級事件,YMS是批次/日級彙總——「一刀切」儲存是常見錯誤。
> - 有價值的分析幾乎都需要跨系統取數,典型鏈路為「Lot→Equipment→Chamber→FDC Trace→缺陷→良率損失」。
> - 跨系統關聯的主要難點是主鍵不一致、時間對齊與多版本狀態,需要在數據治理階段系統解決。

## 28.2 數據血緣與隱性知識:數據從哪來、到哪去、誰懂它

> **本節核心問題**:晶圓廠的數據往往經過了複雜的加工鏈路,這些加工邏輯封裝在哪裡?為什麼這些「看不見的知識」是數據治理的最大障礙?

上一節我們建立了數據源的完整地圖。但現實中,AI工程師拿到的往往不是原始數據,而是經過層層加工後的「報表數據」。這些加工邏輯——誰是源表、中間做了什麼計算、口徑如何定義——構成了**數據血緣(Data Lineage)**。理解數據血緣,是讓數據可信的第一步;而血緣背後的隱性知識,則是晶圓廠數據治理最棘手也最有價值的部分。

### 28.2.1 晶圓廠數據血緣的複雜性來源

晶圓廠的數據血緣遠比網際網路行業複雜,其根源在於**數十年的IT系統積累**。

我們用一條真實的加工鏈來說明。某晶圓廠BI報表中的「週良率」欄位,其血緣路徑可能是:

```
源表(YMS.WAFER_TEST_RESULT) → Oracle儲存程序(PKG_YIELD.CALC_WEEKLY) 
→ PL/SQL業務邏輯(過濾返工批次、按片折算) → ETL作業(每日增量入資料倉儲) 
→ 資料倉儲視圖(V_YIELD_WEEKLY) → BI報表(週良率KPI)
```

這條鏈路中,任何一個環節的語義丟失,都會讓最終數字「失真」。例如,儲存程序裡有一行`WHERE lot_status != 'R'`——含義是排除返工批次。如果分析人員不知道這個過濾條件,直接對報表數據做統計,就會把「不含返工的良率」當成「全部良率」。

晶圓廠數據血緣複雜性的成因可以歸納為三點:

**數十年積累的遺留系統。** 先進晶圓廠的IT系統往往跨越二三十年,經歷了多輪供應商切換與系統升級。早期的邏輯封裝在Oracle儲存程序、視圖、甚至Cobol程式裡,文件早已遺失,只有程式碼還在運行。

**供應商客製化改造。** MES、YMS等系統通常由多家供應商提供,每家都在標準產品之上做了大量客製化——客製化邏輯以儲存程序、自訂表、外掛的形式散落在各處。這些邏輯是「系統的一部分」,但不在任何標準文件裡。

**人員更替與知識斷層。** 晶圓廠的IT與製程團隊流動頻繁,理解某段儲存程序「為什麼這麼寫」的老員工可能已離職。系統在運行,但「為什麼」已經沒人知道。

血緣斷裂的直接後果,在AI時代被放大了。以虛擬量測(VM)建模為例:工程師拿到一張「良率表」用於訓練模型,卻不知道其中的`YIELD_RATE`欄位到底是CP(晶圓級測試)良率還是FT(成品測試)良率、是否包含返工批次、按片折算還是按盒折算——模型學到的標籤本身就是錯的。**標籤錯誤是AI模型最隱蔽也最致命的錯誤來源**,它不像隨機雜訊那樣可以被正規化抑制,而是系統性偏差,模型越訓練越「自信地錯」。

### 28.2.2 隱性知識的三種形態

數據血緣記錄的只是「數據流經了哪些環節」,但每個環節的**語義**——為什麼這麼算、這個欄位代表什麼、這個異常值是什麼意思——是更深層的知識。我們把這類無法從系統文件直接獲取的知識稱為**隱性知識(Tacit Knowledge)**。在晶圓廠,隱性知識以三種形態存在:

**程式碼中的知識:最可靠但最難讀。** 儲存程序、視圖定義、ETL作業腳本是數據語義的真正「定義者」。它們精確記錄了業務邏輯——過濾了什麼、怎麼折算、預設值是什麼。但這類知識高度依賴閱讀者的技術能力,且常常沒有註解。例如下面這段典型的PL/SQL片段:

```sql
-- 計算週良率(排除返工批次與工程實驗批次)
CREATE OR REPLACE PROCEDURE PKG_YIELD.CALC_WEEKLY (p_week IN VARCHAR2) IS
BEGIN
  INSERT INTO YIELD_WEEKLY (WEEK_ID, PRODUCT, YIELD_RATE)
  SELECT p_week, product_id,
         ROUND(SUM(pass_cnt) / NULLIF(SUM(total_cnt), 0) * 100, 2)
  FROM   WAFER_TEST_RESULT
  WHERE  test_week = p_week
    AND  lot_status != 'R'        -- 排除返工批次
    AND  lot_type != 'E'          -- 排除工程實驗批次
  GROUP BY product_id;
END;
```

這段程式碼的語義——「週良率=通過片數/總片數×100,且排除返工與工程批次」——就藏在兩行`WHERE`條件裡。AI工程師如果不讀程式碼,永遠不知道口徑。

**文件中的知識:最正式但最易滯後。** SOP(Standard Operating Procedure,標準作業程序)、工程變更單(ECN/ECO)、製程規格書(Spec)記錄了業務規則的「官方版本」。但它們的問題是**滯後**——系統程式碼改了,文件常常忘記更新;文件寫的口徑與程式碼實際執行的邏輯可能已經不一致。文件是知識的「應然」,程式碼是知識的「實然」。

**人腦中的知識:最有價值但最易流失。** 資深工程師的經驗是隱性知識最集中的形態。例如:「這個欄位出現-9999時表示感測器離線,不是真實值」「3號蝕刻機的壓力在PM後前兩批會偏高,分析時要剔除」「這個良率公式只適用於沒有經過濕式清洗的產品」——這些經驗沒有寫在任何文件裡,卻直接影響數據分析與模型訓練的成敗。

用「知識三形態」對照表可以直觀展示同一知識在不同載體中的樣子:

| 知識形態 | 載體 | 可靠性 | 可讀性 | 更新即時性 | 流失風險 |
| --- | --- | --- | --- | --- | --- |
| 程式碼中的 | 儲存程序、視圖、ETL腳本 | 高(實然) | 低(需技術能力) | 高(程式碼即現狀) | 低(程式碼還在) |
| 文件中的 | SOP、ECN/ECO、Spec | 中(可能滯後) | 高 | 低(常忘記更新) | 中(文件會遺失) |
| 人腦中的 | 工程師經驗 | 高但未沉澱 | 低(口頭傳承) | 不固定 | 高(離職即流失) |

### 28.2.3 隱性知識流失的業務風險

隱性知識流失不是一個「將來可能發生」的問題,而是晶圓廠每天都在發生的現實。

**案例**:某晶圓廠一位資深YED工程師退休後,團隊發現一張「良率修正係數表」的來歷無人能解釋——它是多年前根據某款產品的缺陷分佈經驗人工標定的,一直被良率分析流程引用。新工程師以為它是標準口徑,將其用於多個專案的良率歸因,導致連續三個月的分析結論出現系統性偏差。事後複盤發現,該係數只適用於已停產的舊產品,且從未經過正式評審。

這個案例揭示了隱性知識流失的三類典型風險:

**數據誤讀。** 不知道欄位口徑、不知道異常值含義,分析結論建立在錯誤理解之上——這是最直接的風險。

**重複造輪子。** 隱性知識沒有沉澱,每個新團隊、每輪人員更替都要重新摸索,晶圓廠每年在「重新理解自己數據」上耗費大量工程師時間。

**AI模型學到錯誤標籤。** 正如28.2.1所述,標籤/口徑錯誤對AI模型是系統性傷害。隱性知識流失直接導致AI專案的數據基礎不可靠。

**合規與稽核困難。** 當被問及「這個數字是怎麼算出來的」時,如果答案依賴某位工程師的記憶,稽核將無法通過。

更深層地看,數據治理的本質不是「管理數據」,而是**知識的捕獲與傳承**。血緣圖譜捕獲程式碼中的知識,數據字典捕獲文件中的知識,專家訪談與知識沉澱捕獲人腦中的知識——三者缺一不可。這正是下一節「數據治理體系」的出發點,也是第21章「Ontology與知識圖譜」的思想源頭。

> **實踐提示:** 隱性知識捕獲不要指望一次性「大工程」。務實的做法是**伴隨式沉澱**:在每次數據問題排查、每個RCA案例、每次口徑確認時,順手把「為什麼」記錄到數據字典或知識庫。一個欄位一個欄位地補,比規劃一個龐大的知識工程更可持續。關鍵是要有人對「這個口徑誰負責解釋」負責。

> **本節小結:**
> - 晶圓廠數據血緣複雜的根源是數十年遺留系統、供應商客製化改造與人員更替,大量業務邏輯封裝在儲存程序與視圖中。
> - 隱性知識有三種形態:程式碼中的(可靠但難讀)、文件中的(正式但滯後)、人腦中的(有價值但易流失)。
> - 隱性知識流失的直接風險是數據誤讀、重複勞動、AI模型學到錯誤標籤、合規稽核困難。
> - 數據治理的本質是知識捕獲與傳承,需要同時覆蓋程式碼、文件與人腦三個載體。

## 28.3 數據治理體系:讓數據可信、可追溯、可複用

> **本節核心問題**:面對品質參差、口徑混亂、血緣不清的數據,晶圓廠如何建立一套讓數據「可信、可追溯、可複用」的治理體系?

28.2節指出了問題——數據血緣複雜、隱性知識分散。本節給出解決問題的工程方法:數據品質、標準化、元數據、血緣採集與儲存。這套體系的目標不是「管理數據」本身,而是讓AI工程師和分析師拿到數據時,能夠**信任它、追溯它、複用**它。

### 28.3.1 數據品質挑戰

晶圓廠數據品質問題的典型形態可以歸納為四類,每一類都用真實場景說明:

**缺失值。** FDC訊號在設備PM(預防性維護)後會被重置,PM後前幾批加工可能沒有完整的FDC數據;某些量測點只對抽檢批次執行,導致大量批次在特定欄位上缺失。處理缺失值不能簡單「填零」——需要理解缺失的機制(是隨機缺失、還是與設備狀態相關的非隨機缺失)。

**異常值。** 感測器失效會產生-9999、0等佔位值;設備更換部件後標定漂移,會讓同一製程的參數整體偏移。異常值檢測要與設備事件(更換、PM、警報)關聯起來判斷——同一個數值在PM前後可能一個是異常、一個是正常。

**口徑不一致。** 這是晶圓廠最典型也最危險的問題。以「良率」為例:YED部門定義的是CP測試良率,MFG部門可能用「線良率(Line Yield)」,財務用「綜合良率」,三者口徑完全不同。再如「設備利用率」,不同系統對「可用時間」的定義不同,數字可以差出十幾個百分點。

**時序對齊問題。** 不同機台採樣頻率不同(有的1Hz,有的10Hz),設備時鐘與伺服器時鐘存在漂移。在關聯「FDC參數與量測結果」時,時間對齊錯誤會直接導致特徵錯位——把加工前段的壓力關聯到了加工後段的膜厚上。

從AI視角看,數據品質對模型的影響需要特別強調:**模型對系統性偏差(如標籤口徑錯誤)遠比隨機雜訊敏感**。隨機雜訊可以被損失函數的正規化抑制,但系統性偏差會讓模型學到錯誤的規律——而且越複雜的模型,越容易「記住」這些錯誤規律。因此,數據品質治理必須優先於模型調參,這是AI專案的第一原則。

> **實踐提示:** 晶圓廠數據品質的排查,建議從「口徑清單」開始:把最常用的50-100個業務口徑(良率、利用率、循環時間、缺陷密度等)逐一登記其精確定義、來源系統與計算邏輯。多數AI專案的數據問題,最終都能追溯到「口徑沒對齊」而非「數據缺失」。

### 28.3.2 數據標準化與元數據管理

數據標準化的目標是讓不同系統、不同團隊對同一事物有同一稱呼、同一單位、同一編碼。

**命名規範。** 統一設備ID、步驟ID、產品ID的編碼規則。例如,設備ID統一為「製程類別-序號」(ETCH-03),步驟ID統一為「製程類別-步驟號-版本」。看似簡單,卻是跨系統關聯的基礎——28.1.3節提到的主鍵不一致問題,大多能透過命名規範從源頭緩解。

**單位統一。** 同一物理量在不同系統可能使用不同單位(壓力用mTorr還是Pa,溫度用攝氏還是開爾文)。數據進入數據平台時應統一換算,並在元數據中記錄原始單位。

**字典表/編碼表管理。** 缺陷碼、警報碼、狀態碼等枚舉值需要統一的字典表,並納入變更管理——新增一個缺陷碼不能只改一個系統,要同步所有消費方。

**三類元數據管理。** 元數據(Metadata)是「關於數據的數據」,分為三類:

- **技術元數據**:表結構、欄位類型、主外鍵、儲存位置——回答「數據存在哪、長什麼樣」。
- **業務元數據**:欄位的業務含義、口徑說明、負責人、來源系統——回答「這個欄位是什麼意思」,是AI工程師最需要的。
- **操作元數據**:ETL運行日誌、數據更新時間、血緣記錄——回答「數據是否最新、從哪來」。

業務元數據是數據治理的核心產出。以一個「欄位字典條目」為例:

| 元數據項 | 內容 |
| --- | --- |
| 欄位名 | YIELD_RATE |
| 業務含義 | 產品良率(百分比) |
| 精確定義 | CP測試通過晶片數/總晶片數×100,不含返工批次 |
| 計算邏輯 | 源表YMS.WAFER_TEST_RESULT,儲存程序PKG_YIELD.CALC_WEEKLY |
| 數據粒度 | Lot×產品 |
| 取值單位 | %(0~100) |
| 異常值約定 | -9999表示該批次未測,應排除 |
| 來源系統 | YMS |
| 業務負責人 | YED-張三 |
| 更新頻率 | 日批次處理,每日凌晨2點 |

### 28.3.3 數據血緣自動採集的技術路徑

數據血緣的採集有三大技術路徑,各自的自動化程度與局限差異明顯:

**靜態SQL解析(Static SQL Parsing)。** 解析儲存程序、視圖、ETL腳本的原始碼,自動抽取「表→表」「欄位→欄位」的依賴關係。優點是無需侵入運行環境、可批次處理;缺點是覆蓋率有限——遇到動態SQL(拼接的查詢語句)、PL/SQL巢狀邏輯、外部呼叫時,解析器常常失效。對於Oracle儲存程序中常見的`EXECUTE IMMEDIATE`動態SQL,靜態解析幾乎無能為力。

```sql
-- 動態SQL示例:靜態解析無法確定實際查詢的表與欄位
v_sql := 'SELECT ' || v_dynamic_columns || 
         ' FROM ' || v_dynamic_table || 
         ' WHERE week_id = :w';
EXECUTE IMMEDIATE v_sql INTO v_result USING p_week;
```

**執行期稽核(Runtime Auditing)。** 在資料庫層啟用稽核(如Oracle Fine-Grained Auditing)或從應用層攔截實際執行的SQL,捕獲真實的數據讀寫關係。優點是準確(是實際執行的邏輯,而非猜測);缺點是依賴資料庫稽核能力、有效能開銷,且只能覆蓋「被觸發過的路徑」——某些儲存程序分支可能數月沒有執行過,血緣就不完整。

**人工補錄(Manual Annotation)。** 對自動化無法覆蓋的關鍵口徑,由業務/IT人員人工登記血緣關係。優點是準確且能補充語義資訊(不只是「誰依賴誰」,還有「為什麼」)——數據字典、口徑清單本質上都是人工補錄的成果;缺點是依賴流程紀律,需要長期維護。

**「90-9-1」經驗法則**:在成熟晶圓廠,自動化工具通常能解析出約90%的**表級血緣**(哪張表依賴哪張表),約9%需要人工補錄(動態SQL、跨系統數據流),最後約1%的**欄位級語義血緣**(這個欄位為什麼這麼算)幾乎完全依賴人工。**表級血緣解決「數據從哪來」,欄位級語義血緣解決「數據意味著什麼」**——後者才是AI應用真正需要的,而這部分必須有人參與。

### 28.3.4 血緣的圖儲存方案

數據血緣天然是圖結構:表、欄位、儲存程序、報表是節點,依賴關係是邊。儲存方案有兩種主流選擇:

| 維度 | 關聯式資料庫 | 圖資料庫(Neo4j/NebulaGraph) |
| --- | --- | --- |
| 數據模型 | 血緣表(edge表) | 節點+邊原生圖模型 |
| 多跳查詢 | 需多次JOIN,SQL複雜且效能隨跳數下降 | 原生遍歷,多跳查詢效能與可讀性俱佳 |
| 團隊熟悉度 | 高(人人會SQL) | 低(需學習Cypher/GQL) |
| 維運成本 | 低(複用現有DB) | 中(新元件、叢集維運) |
| 適合規模 | 數千節點以內 | 數萬節點以上 |

**務實建議**:血緣分三個階段演進——起步階段用關聯式資料庫(兩張表:`node`表、`edge`表)即可,支援「欄位→上游欄位」這類單跳查詢;當圖譜規模達到數萬節點、需要頻繁做「從某個欄位出發找出所有下游報表」的多跳遍歷時,遷移到圖資料庫;過渡方案是「關聯式儲存+記憶體圖遍歷」——用Python的networkx在記憶體中構建圖,既保留關聯式的可靠儲存,又獲得圖遍歷的能力,適合中等規模場景。

> **實踐提示:** 血緣分階段演進的關鍵是**數據模型先行**:無論用什麼儲存,血緣的節點/邊/屬性模型(節點類型:表/欄位/程序/報表;邊類型:讀取/寫入/衍生;屬性:來源系統、口徑說明、負責人)要在一開始就設計好。儲存方案可以換,數據模型換了代價就大了。

> **本節小結:**
> - 晶圓廠數據品質的四類典型問題是缺失值、異常值、口徑不一致與時序對齊,其中口徑不一致對AI模型的傷害最大。
> - 數據標準化(命名、單位、字典表)是跨系統關聯的基礎;三類元數據中,業務元數據(欄位字典)是AI工程師最需要的治理產出。
> - 血緣採集有三條路徑:靜態SQL解析(自動化覆蓋表級)、執行期稽核(準確但有開銷)、人工補錄(欄位級語義的「最後一公里」必須靠人)。
> - 血緣儲存可按規模演進:關聯式→記憶體圖遍歷→圖資料庫,但血緣數據模型應一開始就設計好。

## 28.4 工業語義層與知識圖譜:讓AI懂晶圓廠的語言

> **本節核心問題**:解決了數據品質與血緣之後,還有一個更深層的問題——如何讓AI「理解」晶圓廠數據的業務語義,而不是只把它們當作一張張孤立的表?

前兩節我們解決了「數據可信」問題,但「數據可理解」問題依然存在。AI工程師面對的是`EQP_TBL`、`RECIPE_HDR`這樣的物理表,而業務問題用的是「這台設備」「這批晶圓」「這道製程」這樣的業務語言。兩者之間的鴻溝,需要**工業語義層(Industrial Semantic Layer)**來填補。

### 28.4.1 為什麼網際網路數據中台模式不能直接照搬

過去十年,網際網路行業的數據中台(Data Middle Platform)模式被廣泛宣傳:數據湖彙聚全域數據、寬表統一了口徑、BI報表服務決策。這套模式在網際網路場景取得了成功,但晶圓廠不能直接照搬,原因在於工業數據與網際網路數據存在本質差異:

**工業數據的物理錨定性。** 網際網路的一條點擊記錄,脫離上下文仍是一段有意義的日誌;但工業數據的一個壓力讀數,必須對應到「哪台設備、哪個腔體、哪個時刻、哪道製程」,脫離物理上下文就是無意義的數字。物理錨定性要求數據模型必須保留完整的設備-腔體-時間-製程維度,這對「數據湖+寬表」模式提出了額外要求——寬表如果不保留這些維度,數據就失去了工業價值。

**領域語義密度高。** 網際網路數據的欄位語義相對簡單(使用者ID、時間、行為類型),而晶圓廠數據中,同一個欄位`PRESSURE`在不同機台、不同製程、不同Recipe下的含義和取值範圍完全不同;同一個業務概念(如「良率」)在不同部門有不同口徑。這種「上下文決定語義」的特徵,是網際網路數據中台很少遇到的。

**即時性要求與閉環回饋。** 網際網路中台主要用於事後分析(報表、推薦),而晶圓廠數據要支援即時控制(R2R控制、FDC警報)與決策閉環。數據從「被分析」到「被使用」再到「回饋回產線」,鏈路必須閉環,這超出了「取數-分析-報表」的中台範疇。

**結論**:網際網路中台模式解決了「取數」問題(把數據集中起來),但解決不了「語義理解」問題(讓使用者知道數據意味著什麼)——這正是工業語義層要補上的。中台是「數據的搬運工」,語義層是「數據的翻譯官」。

### 28.4.2 工業語義層的概念與定位

**工業語義層的定義**:在物理數據層(資料庫、檔案、設備數據)與AI應用層之間,建立一層「業務物件語義抽象」,讓應用面對的是「批次(Lot)、晶圓(Wafer)、設備(Equipment)、製程步驟(ProcessStep)、缺陷(Defect)、參數(Parameter)」這樣的業務概念,而非`EQP_TBL`、`RECIPE_HDR`這樣的物理表。

用一個類比來理解:語義層是**晶圓廠的「翻譯層」**——把IT工程師能讀的表結構,翻譯成製程工程師和AI工程師能懂的業務語言。傳統模式下,AI工程師問「查一下3號機的良率」,需要自己寫SQL去JOIN四五張表、還要知道3號機對應哪個設備ID;有了語義層,他只需要說「查詢設備=ETCH-03,指標=良率」,語義層負責翻譯成底層查詢。

工業語義層的三重價值:

- **屏蔽底層複雜性**:應用不再需要關心物理表結構、主鍵對映、跨系統關聯,這些都由語義層封裝。
- **統一了口徑**:所有消費方經由同一語義層取數,自然使用同一口徑——28.3節治理出來的口徑清單,透過語義層固化為統一的業務物件定義。
- **受控的數據消費介面**:AI應用(尤其是LLM/Agent)不直接存取底層資料庫,而是透過語義層提供受控介面消費數據——這既是安全邊界,也是權限控制的落點(詳見28.5.3)。

**語義層架構圖(文字描述)**:三層結構。底層為**物理數據層**,包含MES資料庫、YMS資料庫、FDC時序庫、檢測影像儲存等;中間為**工業語義層**,由本體模型(Ontology)與語義服務組成——本體定義業務物件與關係,語義服務提供物件查詢、關係遍歷、口徑計算三類能力;上層為**AI應用層**,包括良率分析、虛擬量測、根因分析、LLM/Agent應用等。數據流向上:A應用透過語義API查詢,語義層翻譯為物理查詢並執行權限過濾,返回業務物件層級的結果。權限控制點位於語義層與物理層之間——所有物理存取都經過語義層的鑑權與過濾。

### 28.4.3 半導體領域本體模型(Ontology)設計

語義層的核心是**本體模型(Ontology)**——對業務實體、關係與規則的顯式形式化描述。晶圓廠語義層可以從一個最小核心本體起步:六個實體、幾組關係。

**六大核心實體**:

| 實體 | 含義 | 關鍵屬性(示例) |
| --- | --- | --- |
| Lot | 批次,晶圓加工的基本管理單元 | LotID、產品、製程路線、狀態 |
| Wafer | 晶圓,物理加工物件 | WaferID、所屬Lot、目前步驟 |
| Equipment | 設備(含Chamber腔體) | EquipmentID、製程類別、狀態 |
| ProcessStep | 製程步驟(Recipe的執行) | StepID、Recipe名、參數版本 |
| Defect | 缺陷 | DefectID、類型、座標、尺寸 |
| Parameter | 製程參數(量測或FDC) | 參數名、數值、時間戳 |

**實體間核心關係**:

```
Wafer -BELONGS_TO-> Lot           (晶圓屬於批次)
Wafer -PROCESSED_ON-> Equipment   (晶圓在設備上加工)
Equipment -EXECUTES-> ProcessStep (設備執行製程步驟)
Defect -OBSERVED_ON-> Wafer       (缺陷在晶圓上被觀測到)
ProcessStep -HAS_PARAMETER-> Parameter (製程步驟有參數)
Lot -HAS_TEST_RESULT-> 良率數據    (批次有測試結果)
```

**RCA場景走查**:用一個具體的根因分析場景,展示「在語義層思考」與「在表裡join」的差別。問題:「某批晶圓良率驟降,找出可能的根因」。在傳統表模式下,工程師需要知道YMS、MES、FDC三套系統的表結構,手工JOIN。在語義層模式下,查詢路徑是:

1. 從語義層定位「良率異常」物件:查詢該Lot的良率數據,確認異常;
2. 沿`Defect -OBSERVED_ON-> Wafer`找到異常良率對應的缺陷及其空間分佈(晶圓圖);
3. 沿`Wafer -PROCESSED_ON-> Equipment`找到加工這些Wafer的設備與腔體;
4. 沿`Equipment -EXECUTES-> ProcessStep`定位到具體製程步驟;
5. 沿`ProcessStep -HAS_PARAMETER-> Parameter`對比該步驟的參數與正常批次,找出偏離。

整個過程不需要碰任何一張物理表——語義層把「業務查詢」翻譯成了「圖遍歷+屬性查詢」。更重要的是,這種查詢路徑是**可解釋**的:每一步都對應明確的業務關係,AI應用給出的結論可以追溯到具體的本體路徑(這正是28.5節GraphRAG的基礎)。

**形式化程度選擇**:本體不需要一開始就採用OWL/RDF這樣的W3C標準。務實路徑是從輕量形式起步:先用屬性圖(property graph)或JSON Schema定義實體與關係,滿足應用需求;當需要跨組織共享、推理能力(如一致性檢查)時,再升級到RDF/OWL。**不迷信標準,按需演進**——本體的價值在於「顯式表達業務語義」,而非「使用了某個標準」。

### 28.4.4 知識圖譜的分層架構

本體模型回答「業務物件長什麼樣」,而完整的晶圓廠知識體系需要三層圖譜協同:

- **L1 數據血緣圖譜(Data Lineage Graph)**:表、欄位、儲存程序、ETL作業、報表之間的依賴關係。回答「數據從哪來」。它是數據治理的產出(見28.3節),也是整個知識體系的地基。
- **L2 業務知識圖譜(Business Knowledge Graph)**:業務實體、業務規則、SOP、歷史案例、缺陷知識的關係網路。回答「業務怎麼運轉」。例如「邊緣環形缺陷→微影焦點偏移→檢查FEM窗口」這條業務規則,就是L2圖譜中的一條知識。
- **L3 可操作本體(Operational Ontology)**:以語義層為核心,實體、關係、動作(Action)可被系統呼叫。回答「AI能做什麼」。例如,本體中的`hold_lot`(凍結批次)動作,可以被Agent執行——這是從「知識」到「行動」的關鍵一躍。

**三層的關係**:L1是地基(L3依賴L2,L2依賴L1);L2在L1之上生長,把技術血緣「翻譯」成業務語義;L3以L2為基礎增加可操作性。架構上,LLM/Agent只與L3互動,L3向下引用L2的知識與L1的血緣——這保證了AI不直接觸碰原始數據,所有存取都經過語義層的受控介面(呼應28.5.3安全設計)。

**知識圖譜分層架構圖(文字描述)**:自下而上三層。L1層以表、欄位、儲存程序為節點,邊為讀取/寫入/衍生關係,是自動+人工採集的血緣圖譜;L2層以業務實體(Lot、Wafer、Equipment、Defect、Rule、SOP、Case)為節點,邊為業務關係(BELONGS_TO、PROCESSED_ON、RULE_OF、CITED_BY),由業務專家與知識工程共建;L3層在最上方,以核心本體物件為節點,增加Action邊(hold_lot、create_workorder、release_lot),Agent透過L3的API消費知識並執行動作。數據流向:Agent請求→L3動作/查詢→L2業務語義→L1物理數據。

### 28.4.5 與業界方案的對比

晶圓廠語義層與知識圖譜並非全新概念,業界已有可參照的方案:

**Google One Knowledge Federation(OKF,統一知識聯邦)**。OKF的理念是「把知識從分散的系統中聯邦起來,提供統一語義視圖」。它與「晶圓廠跨MES/FDC/YMS統一語義視圖」的思路同源——都強調不搬數據,而是建立跨源的語義對映。區別在於,OKF面向網際網路規模的知識組織,晶圓廠需要的是工業物理語義(設備-腔體-時間錨定),這超出了OKF的通用場景。

**Palantir Ontology(本體論平台)**。Palantir在工業領域(尤其是半導體)有成熟落地:其「物件-連結-動作(Object-Link-Action)」模型與本書L3可操作本體直接對應——物件是業務實體,連結是實體關係,動作是可執行的操作。Palantir幫助三星提升良率的案例(見第21章)正是「語義層+AI」在晶圓廠的工業級驗證。其核心思想可以借鑑:物件化抽象、統一語義、動作可執行。

| 方案 | 核心思想 | 與本章的關係 |
| --- | --- | --- |
| Google OKF | 跨源統一語義視圖,知識聯邦 | 與跨系統統一語義目標同源,但非工業專用 |
| Palantir Ontology | 物件-連結-動作,工業落地成熟 | L3可操作本體的直接參照(三星/默克Athinia案例) |
| 本章方案 | 三層圖譜+語義層,按晶圓廠實際演進 | 吸收「物件化、語義統一、可操作」三個思想 |

**務實態度**:不必照搬任何一家。晶圓廠應從最小核心本體起步(六個實體、幾組關係),先支援1-2個高價值場景(如良率RCA),再逐步擴充——本體是「長」出來的,不是「設計」出來的。吸收「物件化、語義統一、可操作」三個思想,按自身系統現狀與團隊能力推進,比追求「一步到位」的方案更可靠。

> **實踐提示:** 本體的「最小可用」邊界怎麼定?一個實用判據:**能支撐你下一個AI應用的查詢路徑即可**。如果下一個應用是良率RCA,本體先覆蓋Lot/Wafer/Equipment/ProcessStep/Defect/Parameter六實體及關聯就夠了;不要為了「完整」而把SOP、人員、成本全部建模——那會讓本體建設停滯在「建模型」階段,遲遲無法產生業務價值。

> **本節小結:**
> - 網際網路數據中台解決「取數」,工業語義層解決「語義理解」;工業數據的物理錨定性與高領域語義密度決定了不能照搬中台模式。
> - 工業語義層是物理數據與AI應用之間的「翻譯層」,三重價值是屏蔽複雜性、統一口徑、受控消費。
> - 晶圓廠核心本體從六實體(Lot/Wafer/Equipment/ProcessStep/Defect/Parameter)起步,本體查詢路徑本身可解釋,是RCA與GraphRAG的基礎。
> - 知識圖譜分三層:L1血緣(數據從哪來)、L2業務知識(業務怎麼運轉)、L3可操作本體(AI能做什麼);Agent只與L3互動。
> - 參照OKF與Palantir Ontology的思想,但按晶圓廠實際最小可用起步,不迷信標準、不一步到位。

## 28.5 LLM與Agent的數據消費模式:從「查數據」到「用數據決策」

> **本節核心問題**:有了語義層與知識圖譜之後,LLM和Agent如何安全、有效地消費這些數據?不同的檢索與協作模式各有什麼優劣?

28.4節建立了語義層與三層知識圖譜——這是AI消費數據的基礎設施。本節討論「最後一公里」:大語言模型(LLM)和智慧體(Agent)如何真正使用這套設施。三個關鍵問題:用什麼檢索方式(向量RAG還是GraphRAG)?多Agent如何協作?數據存取權限如何控制?

### 28.5.1 GraphRAG vs 傳統向量RAG

RAG(Retrieval-Augmented Generation,檢索增強生成)是讓LLM「外掛知識」的主流技術。晶圓廠場景下有兩條路線:

**傳統向量RAG(Vector RAG)**。將文件或數據切塊,用嵌入模型(Embedding Model)向量化,檢索時計算語義相似度,把最相似的文字塊拼進Prompt交給LLM。優點是實現簡單、對開放式問答友善(如「SOP裡關於清洗製程的要求有哪些」)。局限是**沒有多跳推理能力**:它只能檢索「文字相似」的內容,無法回答需要跨實體關聯的問題。例如問「這批晶圓良率下降,和ETCH-03這台設備近三天的參數漂移有沒有關係?」——這需要把批次、設備、FDC參數、缺陷四個維度的數據關聯起來,向量相似度檢索做不到。

**GraphRAG(Graph-based RAG,圖增強檢索)**。在知識圖譜(28.4節的三層圖譜)上進行檢索:先根據問題定位圖譜中的相關子圖(涉及哪些實體、沿哪些關係),再把子圖內的實體、關係與屬性作為結構化上下文交給LLM。優點:

- **可回答多跳問題**:沿本體路徑遍歷,天然支援「批次→設備→參數→缺陷」這樣的跨實體推理;
- **可解釋**:LLM的答案可以追溯到具體的圖譜路徑(哪個實體、哪條關係),工程師能驗證「它為什麼這麼說」;
- **答案更精準**:結構化上下文比文字切片資訊密度高,幻覺率更低。

代價是:需要先建設知識圖譜(成本高、週期長),檢索鏈路也更複雜(定位子圖+組裝上下文)。

**工業場景的選型結論**:

| 維度 | 向量RAG | GraphRAG |
| --- | --- | --- |
| 適用問題 | 文件/規範問答(SOP、Spec、機理) | 數據查詢與關聯分析(良率、設備、批次) |
| 多跳推理 | 不支援 | 支援(沿圖譜路徑) |
| 可解釋性 | 低(僅文字來源) | 高(可追溯到圖譜路徑) |
| 建設成本 | 低(只需文件+embedding) | 高(需知識圖譜) |
| 幻覺風險 | 較高 | 較低(結構化上下文) |

**實際落地中兩者常組合使用**:GraphRAG回答結構化數據問題(查良率、查關聯),向量RAG回答知識文件問題(查SOP、查規格)。一次「良率異常診斷」會話中,可以先由GraphRAG定位數據證據,再由向量RAG補充製程機理知識。

**對比案例**:使用者問「某批次良率下降,哪個腔體參數異常?」向量RAG會回傳若干語義相似的文字片段(可能是無關的設備手冊段落),無法給出結構化答案;GraphRAG會沿本體路徑:定位該批次的良率數據→找到加工設備與腔體→檢索對應時段的FDC參數→比對正常基線,輸出「ETCH-03腔體壓力在X時段偏離基線12%,與良率下降的時間窗口吻合」——並附上圖譜路徑供工程師核驗。

### 28.5.2 多Agent協作架構設計

單個LLM呼叫難以完成複雜的工業任務,晶圓廠實踐中常採用多Agent協作。典型的四類Agent分工:

- **感知Agent(Perception Agent)**:監聽數據變化——SPC告警、FDC異常、YMS良率波動,把訊號轉成結構化事件(如「ETCH-03腔體壓力連續3批超標」)。
- **診斷Agent(Diagnosis Agent)**:基於感知事件,沿知識圖譜進行根因分析(使用28.5.1的GraphRAG),輸出候選根因與證據鏈。
- **知識問答Agent(Knowledge QA Agent)**:面向工程師的自然語言問答,檢索SOP、規格、歷史報告(使用向量RAG),補充製程機理知識。
- **執行Agent(Execution Agent)**:在審批與權限約束下執行動作——hold批次、生成工單、建議Recipe調整;執行前必須經過人工審批。

**協作流程(以「某批良率異常」為例)**:

```
感知Agent觸發(SPC告警:良率低於管制下限)
  → 診斷Agent沿本體推理(GraphRAG定位缺陷→設備→參數證據)
  → 知識問答Agent補充上下文(向量RAG檢索同類案例與SOP)
  → 執行Agent給出建議(候選根因+建議動作)
  → 人工審批(工程師確認或駁回)
  → 執行動作(hold批次/生成工單)並記錄稽核日誌
```

**人在環路(Human-in-the-Loop)設計**是工業場景與網際網路場景的重要差異:Agent只做「建議者」,關鍵動作(hold批次、改Recipe、放行)必須人工審批。原因是晶圓廠動作的代價極高——誤hold一個批次可能損失數十萬美元,誤放行可能導致批量報廢。Agent可以加速分析、提供建議,但最終決定權必須保留給工程師。這既是技術約束,也是合規與責任要求。

> **實踐提示:** 多Agent落地最常犯的錯誤是一上來就做「全自動閉環」。務實的路徑是**先做「分析增強」再做「執行自動化」**:第一階段,Agent只輸出診斷報告與建議,工程師手動執行;第二階段,對低風險動作(如生成報表、查詢數據)開放自動執行;第三階段,才考慮對高風險動作(如hold批次)在嚴格審批下執行。讓工程師先「信任」Agent的分析能力,再「授權」它的執行能力。

### 28.5.3 數據權限與安全控制

LLM與Agent接入數據後,安全成為首要問題。核心原則:**LLM不直接存取底層資料庫**,所有數據消費經由語義層,語義層實現列級/欄位級權限過濾。

**為什麼這樣設計**:

- **提示詞注入(Prompt Injection)風險**:數據中可能包含惡意指令(如某條SOP文件裡寫著「忽略之前的指令」),LLM直接讀庫可能被誘導執行危險操作。語義層作為中間層,限制了LLM能看到的範圍與能執行的查詢。
- **越權查詢風險**:LLM可能生成超出使用者權限的查詢(如跨客戶查詢、存取敏感欄位)。語義層在翻譯查詢時執行權限校驗,拒絕越權請求。
- **最小數據暴露原則**:模型不應接觸它不需要的敏感數據——客戶產品資訊、IP相關的Recipe細節、薪資與成本數據。語義層按角色只暴露必要欄位。

**安全控制的三要素**:

- **存取控制**:語義層實現角色-權限對映(製程工程師可查FDC與量測、設備工程師可查設備日誌、管理層可查成本KPI),查詢執行前做權限過濾。
- **稽核日誌**:記錄「誰(使用者/Agent)透過什麼介面查了什麼數據、執行了什麼動作」,支援事後追溯——這是合規稽核的基礎。
- **敏感欄位脫敏**:客戶ID、產品代號等欄位在回傳給LLM前脫敏或泛化,防止模型「記住」敏感資訊。

**與代工服務轉型的銜接**:第13章討論的代工服務轉型期,核心任務之一是數據安全與多客戶隔離。本節的語義層安全設計正是這一需求的技術基礎——透過語義層實現租戶級隔離(客戶A的Agent看不到客戶B的數據),與第13章「數據安全」和第21章Palantir的「物件-連結-動作」模型形成呼應。

> **本節小結:**
> - 數據查詢/關聯類問題優先GraphRAG(可多跳、可解釋),文件/規範類問題向量RAG夠用,兩者常組合使用。
> - 多Agent協作採用感知-診斷-知識問答-執行四類分工,核心是「人在環路」——Agent做建議者,人做決定者。
> - 安全原則是LLM不直接存取底層資料庫,全部經由語義層做權限過濾、稽核與脫敏。
> - 語義層安全設計為代工服務的多客戶數據隔離提供了技術基礎。

## 28.6 落地路徑與分階段實施:從數據到價值的路線圖

> **本節核心問題**:前面五節建立了從數據源到語義層的完整技術框架,但落地從哪裡開始?如何避免「建了一大堆設施,卻沒產生業務價值」?

技術框架清晰之後,落地路徑決定成敗。晶圓廠數據體系建設的最大風險不是技術難度,而是**節奏失控**——要麼一上來追求完美(本體建了三個月還沒用過),要麼跳過治理直接上AI(模型學到錯誤標籤)。本節給出經過驗證的四階段路線圖,每個階段都有明確的里程碑與驗收標準。

### 28.6.1 四階段路線圖總覽

**階段一:數據排毒與血緣基線(1-3個月)**。目標:搞清楚「數據在哪、長什麼樣、誰依賴誰」。具體工作:

- 盤點全部核心數據源,建立數據源清單(對照28.1節的七大数据源);
- 為Top關鍵欄位建立業務元數據(對照28.3.2的欄位字典);
- 搭建數據血緣基線(靜態解析+人工補錄,對照28.3.3);
- 建立基礎數據品質規則(缺失、異常、口徑)並上線自動預警。

**階段二:語義層構建與單點PoC(3-6個月)**。目標:用一個高價值場景證明「語義層+AI」的價值。具體工作:

- 設計並實作最小核心本體(六實體,對照28.4.3);
- 構建語義層MVP(物件查詢、關係遍歷、口徑計算三類能力);
- 選擇一個高價值場景(通常是良率RCA或虛擬量測)做通「查詢→分析→結論」閉環;
- 產出可量化的價值證明(如RCA耗時從X天降到Y小時)。

**階段三:多Agent協作與閉環驗證(6-12個月)**。目標:從「單點分析」走向「協作閉環」。具體工作:

- 在語義層上構建四類Agent(對照28.5.2);
- 打通「感知→診斷→建議」鏈路,先做分析增強(Agent出報告,人執行);
- 小範圍試點(單部門、單產品線),驗證穩定性和價值;
- 建立人工審批流與稽核機制。

**階段四:Ontology深化與規模化推廣(12-24個月)**。目標:從「試點」走向「規模化」。具體工作:

- 本體擴充(增加動作、規則、歷史案例,升級L3可操作本體);
- 推廣到多部門(製程、設備、製造、品質);
- 建立持續治理營運機制(口徑變更管理、本體版本管理、知識補錄流程);
- 形成「數據-知識-決策」的自增強閉環——每一次RCA的結果沉澱為圖譜中的新知識,反過來提升下一次診斷的品質。

### 28.6.2 各階段關鍵里程碑與驗收標準

每個階段都需要「可衡量的業務價值」作為驗收標準,而不是「技術功能完成」:

| 階段 | 關鍵里程碑 | 驗收標準示例 |
| --- | --- | --- |
| 階段一 | 數據源清單、欄位字典、血緣基線、品質規則 | 核心數據源100%入清單;Top20關鍵口徑有業務元數據;表級血緣覆蓋率≥80%;品質規則上線並自動預警 |
| 階段二 | 核心本體、語義層MVP、PoC閉環 | 本體覆蓋六大實體;語義層支撐至少3類典型查詢;PoC場景端到端跑通且結論與人工一致率≥90% |
| 階段三 | 四類Agent、協作鏈路、試點 | 4類Agent全部可運行;端到端示例(異常→診斷→建議)在試點範圍穩定運行;人工審批流閉環;延遲與吞吐達標 |
| 階段四 | 本體擴充、多部門推廣、治理機制 | 本體覆蓋新增實體與動作;≥2個部門規模化使用;半年內支撐≥N次真實決策;建立持續治理營運機制 |

> **實踐提示:** 階段二選PoC場景有三個判據:一是**數據就緒**(該場景所需的數據已治理、口徑已明確);二是**價值可量化**(能明確說出「現狀耗時X,目標降到Y」);三是**失敗代價可控**(做錯了不影響產線)。良率RCA是首選——數據都在、價值直觀、且是唯讀分析不觸碰產線。避免選「設備即時控制」這類高風險場景作為第一個PoC。

### 28.6.3 常見陷阱與避坑指南

**陷阱一:一上來就追求完美本體。** 本體是「長」出來的,不是「設計」出來的。追求覆蓋全部實體與關係,會導致「建了三個月本體還沒用過一次」。建議從最小可用本體起步(六實體),邊用邊擴——本體的每一次擴充,都應該來自一個真實的查詢需求。

**陷阱二:數據品質拖死AI專案。** AI模型的錯誤大多源自「標籤/口徑錯誤」而非「演算法不好」。跳過階段一直接上AI,模型學到的規律可能是錯的。**數據治理要優先於模型調參**——先用欄位字典與血緣解決「標籤對不對」,再討論「模型準不準」。

**陷阱三:忽略隱性知識的「人」。** 血緣和字典只能記錄「已經知道的」知識,無法捕獲「人腦中的」經驗。關鍵知識必須透過專家訪談、RCA複盤補錄,並且要**制度化**——設立數據管家(Data Steward)角色,讓「每個關鍵口徑有人負責解釋」成為組織規則,而不是個人自覺。

**陷阱四:LLM權限失控。** 先立安全邊界(語義層權限+審批流),再放開Agent能力。不要「先開放後補救」——LLM接入數據後,一次越權查詢或一次提示詞注入的代價,可能遠超省下的開發時間。

**陷阱五:組織協同缺位。** 數據治理必須IT、製程、設備、品質多部門共建。單部門主導容易做成「IT的數據字典」——技術正確但脫離業務。建議成立跨部門的數據治理工作組,由業務部門提出口徑定義,IT部門負責技術實作,品質部門負責驗收。

> **本節小結:**
> - 落地分四階段:數據排毒與血緣基線→語義層與單點PoC→多Agent協作閉環→Ontology規模化,每階段1-3個月到12-24個月不等。
> - 驗收標準必須「價值可量化」(如RCA耗時X天→Y小時),而非「技術功能完成」。
> - 五個常見陷阱:完美本體、數據品質拖死AI、忽略隱性知識的人、LLM權限失控、組織協同缺位。
> - 核心節奏原則:數據治理優先於模型調參,最小可用起步,安全邊界先於能力開放。

## 本章小結

晶圓廠數據體系是全書AI應用的地基。本章沿著「數據是什麼→數據可信嗎→數據可理解嗎→AI怎麼用→怎麼落地」的邏輯,給出了完整的答案:

**數據是什麼**:晶圓廠有七大核心數據源,時間粒度從毫秒(FDC)到天級(ERP)跨越六個數量級,任何有價值的分析都需要跨系統取數。

**數據可信嗎**:數據血緣複雜、隱性知識分散,需要透過數據治理(品質、標準化、元數據、血緣)讓數據可信、可追溯、可複用——數據治理的本質是知識捕獲與傳承。

**數據可理解嗎**:網際網路中台解決不了工業語義理解問題,晶圓廠需要工業語義層與三層知識圖譜(L1血緣→L2業務知識→L3可操作本體),讓AI以業務物件而非物理表的方式理解數據。

**AI怎麼用**:數據查詢類問題用GraphRAG,文件類問題用向量RAG;多Agent協作採用感知-診斷-問答-執行分工,人在環路;安全上LLM不直接存取資料庫,全部經由語義層受控消費。

**怎麼落地**:四階段路線圖——數據排毒與血緣基線→語義層與單點PoC→多Agent協作閉環→Ontology規模化,每個階段都要有可衡量的業務價值。

對晶圓廠而言,數據體系建設的真正目標不是「建成一座數據平台」,而是**讓數據成為可信任、可理解、可行動的組織資產**。當工程師和AI系統都能基於同一套可信語義思考時,後續章節討論的良率預測、虛擬量測、預測性維護、根因分析等AI應用,才有了堅實的立足之地。
