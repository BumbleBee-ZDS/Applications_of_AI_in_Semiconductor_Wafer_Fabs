## Project Overview

This project is a minimal runnable Demo (MVP) for the "defect root-cause analysis" business scenario in a semiconductor fab, demonstrating a typical multi-agent collaboration flow:

```
User question  →  Planner (decomposes subtasks)
              →  ToolSet (query lot / query tool / query recipe / query history)
              →  Reflector (checks data contradictions)
              →  Orchestrator (main loop + failure self-healing)
              →  final root-cause report + recommendations
```

Meanwhile, the `Evaluator` collects metrics in real time while the Agents run:

| Dimension | Metrics |
|---|---|
| **Process quality** | executed step count (max 6), whether the Reflector found data contradictions |
| **Resource cost** | total tool-call count, simulated token consumption (1 char = 1 token) |
| **System resilience** | retry count, whether a dead loop occurred, whether timeouts were handled gracefully (resilience score) |
| **Business value** | whether the final conclusion contains actionable "recommendations" |

## Business Scenario

**User role**: process engineer

**Example inputs** (enter or select in the UI):

1. `Lot W12345 has out-of-spec critical dimension (CD); analyze the cause.`
2. `Lot W12346 has small CD; investigate possible contributing factors.`
3. `Lots W12350 and W12351 both show CD out-of-spec on ETCH-CH-007; is there a correlation?`

**The system must sequentially complete**:

```
Query lot info → Query the corresponding tool (Etch Chamber) run log → Query the latest recipe
→ Reflector detects contradictions → give conclusion + recommendations
```

If the tool interface times out (30% probability): retry once → still failing →
**the Planner automatically adjusts the plan** (degrades to lot-history inference), implementing "failure self-healing".

## Agent Architecture (White-Box Modules)

### 1. Memory
Core ability: stores the lot number (Lot ID), preventing the Agent from forgetting during multi-step execution.
```python
m = Memory()
m.store("lot_id", "W12345")
m.recall("lot_id")   # → "W12345"
```
- Future extensions: persistent JSON storage / vector long-term memory / sliding window.

### 2. ToolSet
4 Mock tools, all recorded by the Evaluator for `tool_call_count` and dead-loop signatures:

| Tool | Stability | Description |
|---|---|---|
| `get_lot_info(lot_id)` | ✅ stable | Returns product, CD target/measured, chamber, status |
| `get_equipment_log(chamber_id)` | ⚠ 30% timeout | Returns pressure/RF power/temperature; **auto-retries once** |
| `get_recipe_params(lot_id)` | ✅ stable | Returns recipe_id, set-point pressure, process time |
| `get_lot_history(lot_id)` | ✅ stable | **Fallback tool**, substitutes when the equipment interface is unavailable |

### 3. Planner
- `make_plan(question)` → returns a standard 5-step plan;
- `adjust_plan_skip_equipment(plan)` → failure self-healing: replaces the "tool log" step with "lot-history inference (degraded)"; only one adjustment allowed.

### 4. Reflector
Checks the **consistency** of tool-returned data:

```
recipe.pressure_setpoint  (5.0 mTorr, normal)
      ↕  |delta| > 1.0 → conflict!
equipment_log.pressure    (6.8~7.6 mTorr, abnormal)
```

Sets `Evaluator.reflection_valid = True` when a contradiction is found.

### 5. Orchestrator (main loop)
Schedules steps in order, with built-in dual termination protection:

```python
while idx < len(plan):
    if step_count >= max_steps:           # ① step cap 6
        break
    if evaluator.dead_loop_flag:          # ② same tool + same args for 2 consecutive steps
        break
    # dispatch to step → call ToolSet / Reflector
```

Report generation: `_generate_report()` uses f-string concatenation, **dynamically reading the chamber ID and CD deviation direction** (avoiding hardcoded ETCH-CH-007).

### 6. Evaluator
See the next section.

## Execution Flow

```
User clicks [🚀 Start Analysis]
    │
    ├─ Memory.store(lot_id)
    │
    ├─ Planner.make_plan()
    │   → ["query lot info", "query tool run log", "query recipe", "reflect", "report"]
    │
    ├─ Orchestrator.run()
    │   ├── Step 1  get_lot_info(W12345)     → CD out of spec
    │   ├── Step 2  get_equipment_log(ETCH-CH-007)
    │   │         └─ 30% timeout → retry → still failing →
    │   │            Planner.adjust_plan_skip_equipment()
    │   │            Step 2 replaced by: get_lot_history() (degraded)
    │   ├── Step 3  get_recipe_params(W12345) → recipe set-point pressure 5.0
    │   ├── Step 4  Reflector.check_conflict()
    │   │         └─ recipe 5.0 vs tool 7.1 → contradiction detected!
    │   └── Step 5  _generate_report()  → root cause + 3 recommendations
    │
    └─ Left: logs + report; Right: real-time metric cards
```

## Evaluator (Core)

### Metric List

| Metric | Description | Corresponding principle |
|---|---|---|
| `step_count` | Executed step count (max 6) | Process quality |
| `reflection_valid` | Whether the Reflector found a contradiction | Process quality |
| `tool_call_count` | Total tool-call count | Resource cost |
| `token_cost_mock` | 1 char = 1 token, all outputs accumulated | Resource cost |
| `retry_count` | Retry count after tool timeouts | System resilience |
| `dead_loop_flag` | True if 2 consecutive steps use the same tool and args | System resilience |
| `timeout_handled` | Whether recovered after retry (decides resilience score) | System resilience |
| `resilience_score()` | High (not triggered) / High (self-healed) / Medium (not recovered) | System resilience |
| `business_value()` | Whether the final report contains "recommendations" | Business value |

### Dead-Loop Detection Mechanism

Each tool call generates a signature:
```
"name|args_json_sorted"
```
If two consecutive signatures are identical → `dead_loop_flag = True`, and the Orchestrator forces a break.

### Resilience Scoring Rules

| Scenario | Score |
|---|---|
| `retry_count == 0` | **High** (timeout not triggered) |
| `retry_count > 0 && timeout_handled` | **High** (self-healed) |
| Other (retry still failed, degraded) | **Medium** (retried but not recovered) |

## Streamlit UI Layout

Two-column layout (`st.columns([3, 2])`):

### Left: 🛠 Input & Execution Flow
- **Example-question dropdown**: 6 questions generated by DeepSeek; selecting one auto-fills the input box;
- **Process-engineer question text_input**: manual input or editing;

  `[Planner] / [Tool] / [Reflect] / [Step N] / [Memory]` markers;

### Right: 📊 Evaluation Panel
- `st.metric` 4 cards: executed steps / tool-call count / simulated token cost / retry count;
- `st.success` / `st.error`: dead-loop detection status;
- **Resilience score**: highlighted text;
- `st.warning` / `st.info`: reflection validity;
- `st.success` / `st.error`: business value (whether recommendations exist);
- `st.expander`: full `evaluator.to_dict()` JSON.

```bash
cd fab_agent_test
```

## Generating More Test Data (DeepSeek)

The project includes the `gen_test_data.py` script, which uses the `DEEPSEEK_API_KEY` in `.env` to call the `deepseek-chat` model and batch-generate:

- 8 lots (CD out-of-spec / CD small / thickness abnormal / normal / same-chamber correlation — 5 scenario types in total)
- 8 recipes (one per lot; recipe set-points are normal, creating conflicts)
- 6 natural-language questions (covering single-lot analysis, correlation, and comparative analysis)

### Usage

```bash
python gen_test_data.py
```

Output file: `fab_test_data.json` (automatically **merged** into `LOT_DB` / `RECIPE_DB` on the next `app.py` launch, overriding same-name lots).

### Script Notes

| Item | Description |
|---|---|
| API source | Reads `DEEPSEEK_API_KEY` + `DEEPSEEK_BASE_URL` from `.env` |
| Request library | Standard library `urllib.request` only (no `requests` needed) |
| Output format | Forces `response_format: json_object`; the script does secondary normalization |
| Field validation | `normalize_lot` / `normalize_recipe` fill in missing fields |

## Extension Points

### 1. Connect a Real LLM (replace report generation)
In `core/orchestrator.py`'s `_generate_report()`, replace the current f-string concatenation with a call to DeepSeek / Qwen:
```python
# read .env → urllib.request POST to DEEPSEEK_BASE_URL/chat/completions
# put the return value into report
```
You can also change `Planner.make_plan()` / `Reflector.check_conflict()` to LLM-driven, keeping the same return structure.

### 2. Replace Mock with Real Interfaces
Change `LOT_DB` / `RECIPE_DB` in `data/mock_data.py` to query from MES / DB;
change `core/toolset.py`'s `_call_equipment_api()` to real REST / SECS-GEM calls,
keeping the protocol that timeouts return `None`.

### 3. Add More Agents
Add `reporter.py` (summary-report Agent), `validator.py` (recommendation-executability review) and other modules under `core/`, then add them to the step dispatch in `Orchestrator.run()`.

### 4. Long-Term Evaluation Logs
Append `runs/yyyyMMdd_HHMMSS.json` at the end of `Evaluator.to_dict()` for later batch statistics (A/B comparisons of different Planner strategies).

### 5. DashScope Embedding (already in `.env`)
`QWEN_EMBEDDING_MODEL=qwen3.7-text-embedding` can be used for:
- Vectorizing historical lots' features + similarity retrieval (replacing the current pure string matching);
- Question clustering (grouping by defect type).

## FAQ

**Q1: Why not use LangChain / CrewAI?**
A1: The MVP technical constraints require "all Agent logic hand-written", making it easy to observe each module's behavior and evaluation metrics in a white box; the 6 classes in `core/` total only ≈600 lines of code, with no dependency burden.

**Q2: What if `gen_test_data.py` fails or times out?**
A2: `fab_test_data.json` is **optional** — even if it doesn't exist, `app.py` still demonstrates normally with the built-in 2 lots (W12345 / W67890). On an API Error, check whether `DEEPSEEK_API_KEY` in `.env` is correct.

**Q3: Why doesn't "timeout self-healing" sometimes appear?**
A3: The timeout is a 30% probability (`EQUIP_TIMEOUT_RATE = 0.30`), triggering about once every 3 runs; you can temporarily raise it to `1.0` in `data/mock_data.py` to reproduce the timeout self-healing scenario 100%.

**Q4: Could dead-loop detection "same tool + same args for 2 consecutive steps" be a false positive?**
A4: The Planner's `make_plan()` generates 5 distinct steps each time; it only triggers if a bug makes the Orchestrator repeatedly call the same tool. You can also set the step cap to `max_steps = 6` as a second line of defense.

**Q5: How do you verify whether the report has "business value"?**
A5: `Evaluator.business_value()` currently uses the simple rule `"recommendation" in final_report`. Later you could change it to: check that the recommendation list length ≥ 2, or call an LLM for classification scoring (also can add new fields in the Evaluator).
